## 1. System Overview

### 1.1 System Description

The Cybernetic AI Governance Engine (CAGE) is a HIGH-impact AI governance platform deployed on Google Kubernetes Engine (GKE) in Google Cloud Platform (GCP). It functions as an intelligent financial advisory gateway that enforces real-time policy controls on AI-generated financial recommendations.

CAGE intermediates between end-user financial advisors and large language model (LLM) inference services, applying multi-layered governance:

- **OPA (Open Policy Agent)** enforcing Rego-based access control and trade authorization policies
- **NeMo Guardrails** providing LLM response filtering, PII detection, and dialogue safety
- **LangGraph** orchestrating multi-agent reasoning workflows
- **Compliance Bridge** streaming real-time governance events to audit systems
- **Langfuse** providing LLM observability and trace management

The system handles PII in the context of financial advisory services, including user identity, financial portfolio data, trade requests, and AI interaction logs. Given the HIGH system categorization (FIPS 199), this PIA applies the most stringent privacy analysis consistent with NIST SP 800-122.

### 1.2 Deployment Architecture

| Component         | Technology                     | Privacy Relevance                                |
| ----------------- | ------------------------------ | ------------------------------------------------ |
| API Gateway       | Python FastAPI / gRPC          | Receives user requests containing PII            |
| Governance Engine | OPA + Rego                     | Evaluates requests containing user identity      |
| LLM Inference     | vLLM (self-hosted)             | Processes prompts that may include financial PII |
| NeMo Guardrails   | NVIDIA NeMo                    | PII detection and redaction in LLM I/O           |
| Audit/Telemetry   | OpenTelemetry → Langfuse → GCP | Stores traces with user identifiers              |
| Database          | Cloud SQL (PostgreSQL)         | Persists Langfuse traces and audit records       |
| Object Storage    | Google Cloud Storage           | Stores OSCAL artifacts and audit exports         |
| Secret Management | GCP Secret Manager             | Stores credentials and signing keys              |

### 1.3 System Categorization

- **FIPS 199 Impact Level:** HIGH (Confidentiality: HIGH, Integrity: HIGH, Availability: MODERATE)
- **PII Confidentiality Impact:** HIGH (per NIST SP 800-122 §3.1 — financial PII is inherently sensitive)
- **Reference:** `compliance/categorization/FIPS199_CATEGORIZATION.md`

## 2. Information Collected

### 2.1 PII Categories

The following categories of Personally Identifiable Information (PII) are collected, processed, or generated by the CAGE system:

| PII Category                    | Data Elements                                                                           | Source                                  | Sensitivity |
| ------------------------------- | --------------------------------------------------------------------------------------- | --------------------------------------- | ----------- |
| **User Identity**               | Username, user ID, email (for auth), role/title                                         | Authentication system (GCP IAM / OIDC)  | HIGH        |
| **Financial Portfolio Data**    | Account numbers, portfolio holdings, asset values, trade history                        | User requests to financial advisory API | HIGH        |
| **Trade Requests**              | Trade type, symbol, quantity, dollar amount, user identity                              | User-submitted advisory requests        | HIGH        |
| **AI Interaction Logs**         | User prompts (may contain financial data), AI-generated responses, governance decisions | LangGraph workflow execution            | HIGH        |
| **Authentication Tokens**       | JWT/OIDC tokens, session identifiers, HMAC routing seals                                | Authentication/authorization layer      | HIGH        |
| **Audit Logs**                  | User identifier, action timestamp, request content, governance verdict, policy outcome  | OTel spans → Langfuse → Cloud Trace     | HIGH        |
| **Market Data Requests**        | Ticker symbols associated with user identity and portfolio                              | Market data API integration             | MODERATE    |
| **System Interaction Metadata** | IP address (internal cluster), request latency, model used, node traversal path         | OTel instrumentation                    | MODERATE    |

### 2.2 PII Entity Types Recognized by NeMo Guardrails

The system's NeMo Guardrails PII detection layer (referenced in `config/rails/config.yml`) recognizes and can redact the following 16 PII entity types in AI model inputs and outputs:

1. `PERSON` — personal names
2. `EMAIL_ADDRESS` — email addresses
3. `PHONE_NUMBER` — phone numbers
4. `US_SSN` — Social Security Numbers
5. `US_BANK_NUMBER` — bank account numbers
6. `CREDIT_CARD` — credit card numbers
7. `IBAN_CODE` — international bank account numbers
8. `US_ITIN` — Individual Taxpayer Identification Numbers
9. `US_PASSPORT` — US passport numbers
10. `LOCATION` — geographic locations
11. `DATE_TIME` — dates and times (when associated with identity)
12. `NRP` — Nationality, Religion, Political affiliation
13. `IP_ADDRESS` — IP addresses
14. `URL` — URLs (when containing user identifiers)
15. `MEDICAL_LICENSE` — medical license numbers
16. `ORGANIZATION` — organization names (when linked to individual identity)

### 2.3 PII Not Collected

The following categories of PII are explicitly **not** collected:

- Social Security Numbers (except when inadvertently present in user financial queries — see §2.2 NeMo detection)
- Biometric data
- Medical/health information (not in scope for financial advisory)
- Minors' data (system restricted to professional financial advisors ≥18)

## 4. Purpose and Use of PII

### 4.1 Authorized Purposes

PII collected and processed by CAGE is used exclusively for the following authorized purposes:

| Purpose                        | PII Used                                                 | Legal Basis                         |
| ------------------------------ | -------------------------------------------------------- | ----------------------------------- |
| **Governance Decision-Making** | User identity, role, trade request content               | GLBA safeguards; SEC Reg S-P        |
| **Audit Trail Generation**     | User identifier, action, timestamp, governance verdict   | FINRA Rule 3110 (records retention) |
| **Policy Enforcement**         | User role, account type, trade size                      | GLBA; SEC Investment Advisers Act   |
| **Compliance Reporting**       | Aggregated user action logs (anonymized where possible)  | SEC Reg S-P; FINRA reporting        |
| **AI Safety Monitoring**       | Prompt content, response content (PII-redacted via NeMo) | Internal governance requirement     |
| **Incident Response**          | Full audit logs (PII access restricted to ISSO/IR team)  | NIST SP 800-61r2                    |

### 4.2 Prohibited Uses

PII collected by CAGE is explicitly **prohibited** from use for:

- Training or fine-tuning AI models (user data is not used as training data)
- Marketing or commercial profiling
- Secondary disclosure to non-authorized third parties
- Any purpose inconsistent with the original advisory context

### 4.3 AI-Specific Processing Notice

PII may be included in prompts submitted to the self-hosted vLLM inference service. The NeMo Guardrails layer performs real-time PII detection and redaction before prompts reach the LLM (see §11 — PII Minimization). The self-hosted vLLM deployment ensures financial PII does not leave the organizational boundary to third-party LLM APIs.

## 6. Data Retention

### 6.1 Retention Schedule

| PII Category                                 | Retention Period                                   | Disposal Method                                         | Legal Basis                     |
| -------------------------------------------- | -------------------------------------------------- | ------------------------------------------------------- | ------------------------------- |
| **Audit Logs (Langfuse traces)**             | 7 years                                            | Cryptographic erasure or secure deletion from Cloud SQL | FINRA Rule 4511; SEC Reg 17a-4  |
| **AI Interaction Logs (prompts/responses)**  | 90 days (operational) → 7 years (redacted summary) | Automated purge of raw prompts; summary retained        | Internal governance policy      |
| **Authentication Tokens / Session Data**     | Token validity period (≤8 hours)                   | Automatic expiration; no persistent storage             | GLBA safeguards                 |
| **Financial Portfolio Data (in prompts)**    | Transient (session only); not persisted by CAGE    | Session termination                                     | GLBA; SEC Reg S-P               |
| **Trade Request Records**                    | 7 years                                            | Secure deletion from Cloud SQL audit tables             | SEC Rule 17a-4; FINRA Rule 4511 |
| **OTel Span Metadata (user ID, timestamps)** | 90 days (Cloud Trace)                              | GCP Cloud Trace automatic expiration                    | Operational monitoring          |
| **OSCAL Compliance Artifacts**               | Duration of ATO + 3 years                          | Secure deletion from GCS                                | NIST SP 800-37                  |

### 6.2 NeMo-Recognized PII Entity Retention

The 16 PII entity types enumerated in §2.2 are subject to NeMo Guardrails detection. When detected in AI I/O:

- **Raw PII values are never persisted** in Langfuse traces
- **Redacted placeholders** (e.g., `[PERSON]`, `[US_SSN]`) replace detected PII in stored traces
- Retention of redacted traces follows the AI Interaction Logs schedule (90 days raw → 7 years summary)

### 7.1 Role-Based Access to PII

| Role                             | PII Access                                           | System                  | Access Method                                               |
| -------------------------------- | ---------------------------------------------------- | ----------------------- | ----------------------------------------------------------- |
| **System Administrator**         | Full system access (break-glass)                     | GKE, Cloud SQL, GCS     | GCP IAM — `roles/owner` (break-glass only; MFA required)    |
| **ISSO**                         | Audit logs, compliance reports                       | Langfuse, Cloud Logging | GCP IAM — `roles/logging.viewer`; Langfuse admin            |
| **Financial Advisor (End User)** | Own session data only                                | CAGE API                | OIDC authentication; OPA RBAC enforced                      |
| **Senior Trader**                | Trade requests ≤$500k; audit logs of own activity    | CAGE API                | OPA Rego policy — `cage.io/role: senior-trader`             |
| **Junior Trader**                | Trade requests ≤$5k; audit logs of own activity      | CAGE API                | OPA Rego policy — `cage.io/role: junior-trader`             |
| **Compliance Officer**           | Aggregated audit reports (anonymized where possible) | Compliance Bridge       | OPA policy — `cage.io/role: compliance-officer`             |
| **Security Control Assessor**    | Compliance artifacts (no raw PII)                    | OSCAL artifacts in GCS  | GCP IAM — `roles/storage.objectViewer` on compliance bucket |
| **Incident Responder**           | Full audit logs (time-limited during incident)       | Cloud Logging, Langfuse | Break-glass role + AO notification required                 |

### 7.2 Technical Access Controls

**Kubernetes RBAC:**

- Namespace-level isolation in `governance-stack` namespace
- Lula validation `lula-validation-ac2.yaml` enforces named ServiceAccounts with `cage.io/account-purpose` labels
- Default ServiceAccount has `automountServiceAccountToken: false`

**GCP IAM:**

- Workload Identity Federation (WIF) for GKE-to-GCP service authentication
- Least-privilege IAM bindings per service (see `deployment/terraform/iam_least_privilege.tf`)
- Broad IAM roles (`roles/editor`) identified as gap in POAM-002 — remediation in progress

**OPA Policy Enforcement:**

- Every API request evaluated against `deployment/system_authz.rego`
- Role-based trade limits: junior traders ≤$5k, senior traders ≤$500k
- Fail-closed defaults: unrecognized roles denied all access

**Network Policy:**

- Default-deny ingress and egress in `governance-stack` namespace
- Explicit allowlisting per `deployment/k8s/network-policy.yaml`

## 8. Data Quality

### 8.1 Accuracy

- **User Identity:** Sourced from authoritative OIDC/GCP IAM identity provider; CAGE does not modify identity claims
- **Financial Data:** Sourced from user-submitted requests; CAGE does not independently verify financial data accuracy — this is the responsibility of the upstream advisory system
- **Audit Records:** Generated by OTel instrumentation; timestamps are synchronized via GCP NTP; audit records are append-only and cryptographically signed via HMAC routing seal

### 8.2 Completeness

- All governance decisions generate OTel spans with required AU-12 fields: `iso42001.control`, `iso42001.verdict`, `user`, `timestamp`
- Incomplete spans (missing required fields) are rejected by the compliance bridge
- Lula validation `lula-validation-au12.yaml` monitors telemetry pipeline availability (stub needs update to check Langfuse worker readiness — standalone OTel Collector deprecated 2026-05-31)

### 8.3 Relevance

- PII collection is limited to information necessary for governance decision-making
- NeMo Guardrails PII detection ensures that surplus PII in AI prompts is redacted before storage
- Market data requests are de-linked from user identity where operationally feasible

### 8.4 Data Correction

- Users may request correction of inaccurate identity data through the GCP IAM identity provider (source of truth)
- Audit records are immutable (append-only) — corrections are recorded as new entries, not overwrites, to preserve audit integrity

## 11. PII Minimization

### 11.1 NeMo Guardrails PII Detection

The CAGE system employs NVIDIA NeMo Guardrails with a PII detection and redaction pipeline as a primary minimization control. This layer:

1. **Scans all user prompts** before they reach the vLLM inference service
2. **Detects 16 PII entity types** (see §2.2) using the Presidio-backed `recognize_pii` action configured in `config/rails/config.yml`
3. **Redacts detected PII** by replacing values with type tags (e.g., `[US_SSN]`, `[CREDIT_CARD]`)
4. **Blocks high-risk prompts** containing PII types inconsistent with financial advisory context

### 11.2 Prompt Engineering Minimization

- System prompt templates (`config/rails/`) are designed to elicit financial advisory responses without requiring users to disclose sensitive PII
- OPA Rego policies (`deployment/system_authz.rego`) evaluate trade authorization based on user role and trade parameters — not raw financial account identifiers

### 11.3 Telemetry Minimization

- OTel spans are instrumented at the governance decision level, not the raw request level
- User PII in spans is limited to: `user` (user identifier, not full name), `iso42001.control`, `iso42001.verdict`, `timestamp`
- Full request/response bodies are **not** included in OTel spans by default

### 11.4 Logging Minimization

- Application logs are filtered at the OTel instrumentation layer before export to Langfuse's integrated OTLP ingestion endpoint (standalone `otel-collector` deprecated 2026-05-31)
- Cloud Logging exclusion filters may be configured to further reduce PII in operational logs

## 12. Individual Rights

### 12.1 Right of Access

Individuals whose PII is processed by CAGE may request access to their personal data held in the system. Requests are directed to the designated Privacy Officer.

**Process:**

1. Individual submits written access request to Privacy Officer
2. Privacy Officer verifies identity and authorization
3. Relevant Langfuse traces and audit records are extracted (PII-redacted portions are identified)
4. Response provided within 30 days (or per applicable regulatory timeline)

### 12.2 Right of Correction

Individuals may request correction of inaccurate PII. Since CAGE's identity data derives from the authoritative GCP IAM identity provider:

- Identity attribute corrections must be submitted to the identity provider administrator
- CAGE audit records are immutable — corrections are recorded as new entries with a correction notation to preserve audit integrity

### 12.3 Right of Deletion

Individuals may request deletion of their PII, subject to legal retention obligations:

- **Operational data** (session state, ephemeral prompts): Deleted upon session termination (automated)
- **Audit records:** Subject to FINRA Rule 4511 and SEC Rule 17a-4 7-year mandatory retention — **deletion requests cannot be honored for financial audit records during the retention period**
- **AI interaction logs (raw prompts):** Purged after 90 days per retention schedule; redacted summaries retained 7 years per regulatory requirement

Deletion requests are reviewed by the Privacy Officer and Legal Counsel.

### 12.4 Right to Object / Opt-Out

The CAGE system is an enterprise financial advisory compliance tool — it is not a consumer-facing service. Users are employees or contractors subject to their employment/contractual terms. Individual opt-out from AI governance processing is not available as it would undermine the system's regulatory compliance mission.

### 12.5 Privacy Complaints

Individuals may submit privacy complaints to:

- **Internal:** Privacy Officer (contact TBD upon system authorization)
- **Regulatory:** SEC Office of Investor Education and Advocacy; FINRA Investor Complaint Center (for financial services context)
