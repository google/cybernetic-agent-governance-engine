## 1. Executive Summary

### 1.1 Assessment Overview

This Security Assessment Report (SAR) documents the findings of the initial security control assessment of the Cybernetic AI Governance Engine (CAGE). This assessment was conducted as a pre-authorization gap analysis to characterize the current security posture of the system prior to the formal Security Assessment Plan (SAP) execution scheduled for 2026-Q2.

The assessment evaluated the CAGE system against the NIST SP 800-53 Rev. 5 **HIGH** impact baseline, focusing on 13 priority controls identified through gap analysis. The CAGE system is a novel AI/ML governance and inference gateway for financial services, deployed on Google Kubernetes Engine (GKE) and subject to financial regulatory requirements including SEC Rule 17a-4, FINRA Rule 4511, SEC Reg S-P, and Federal Reserve SR 11-7.

### 1.2 Overall Risk Posture

**Current Risk Rating: HIGH**

The CAGE system currently demonstrates significant security control gaps across access control, identification and authentication, audit and accountability, incident response, and supply chain risk management control families. Key findings include:

- **3 Critical findings** — including absence of intra-cluster mTLS (POAM-013) and HMAC seal bypass vulnerability (POAM-012, now resolved)
- **10 High findings** — including absent account management procedures, overly permissive IAM bindings, no incident response plan, and no container vulnerability scanning
- **2 Moderate findings** — including no encryption-in-transit validation test and no SBOM generation

**RMF Completion Estimate:** ~24% of the full authorization package is complete. Critical gaps include:

- No System Security Plan (SSP) — (POAM-015)
- No Authorization to Operate (ATO) — (POAM-005)
- No formal Incident Response Plan — (POAM-008, partially resolved by `docs/IR_PLAN.md`)
- No container vulnerability scanning in CI/CD — (POAM-010)
- No intra-cluster mTLS — (POAM-013)

### 1.3 Positive Security Findings

The assessment also identified areas of security strength:

- **9 NetworkPolicy objects** implementing default-deny posture across GKE namespace
- **5-tier neuro-symbolic governance pipeline** (NeMo Guardrails → OPA → STPA → OFAC → ISO 42001 evidence)
- **AgentSight eBPF** monitoring providing kernel-level observability
- **OPA RBAC** with Rego policy enforcement for governance decisions
- **OpenTelemetry / Langfuse** audit trail infrastructure (though mock traces identified — POAM-003)
- **ISO 42001 evidence stamping** on AI inference outputs
- **HMAC routing seal** enforcement (bypass now remediated — POAM-012)
- **NeMo Guardrails Presidio** PII detection covering 16 entity types

### 1.4 Authorization Recommendation

Based on the current findings, the assessor **does not recommend ATO issuance** at this time. Remediation of Critical and High findings, particularly POAM-013 (mTLS), POAM-015 (SSP), POAM-005 (ATO package), and POAM-008 (IRP), is required before ATO can be recommended. A conditional ATO (IATO) may be considered by the AO if critical findings are remediated and remaining High findings are captured with credible remediation timelines in the POA&M.

## 2. System Overview

The Cybernetic AI Governance Engine (CAGE) is an AI-native financial advisory platform deployed on Google Kubernetes Engine (GKE) on Google Cloud Platform (GCP). The system orchestrates multi-agent LLM workflows for investment analysis and trade recommendations, enforcing governance policies via a 5-tier neuro-symbolic pipeline.

**Key System Characteristics:**

- **Platform:** GKE, GCP-managed services (Cloud SQL PostgreSQL, GCS, Cloud Trace)
- **Application Stack:** FastAPI/gRPC gateway, NeMo Guardrails, OPA Policy Engine, LangGraph, Redis
- **AI/ML Components:** LangGraph Financial Advisor, vLLM inference, Vertex AI
- **Observability:** AgentSight eBPF, OpenTelemetry, Langfuse
- **Compliance Automation:** Lula (compliance-as-code), OSCAL, ISO 42001 evidence stamps
- **Security Baseline:** NIST SP 800-53 Rev. 5 HIGH

The system processes five information types including PII/Individual Financial Records (IT-004, C=High), which drives the overall HIGH system security category per FIPS 199. See `compliance/categorization/FIPS199_CATEGORIZATION.md` for full categorization detail.

### FIND-001: No Account Management Procedures (AC-2)

**Control:** AC-2 — Account Management
**Severity:** High
**Status:** Open
**POAM Reference:** POAM-001
**Scheduled Completion:** 2026-04-30

**Description:**
No formal account management procedures exist documenting the lifecycle management of user accounts, service accounts, and privileged accounts for the CAGE system. This encompasses GCP IAM accounts, GKE Kubernetes RBAC role bindings, and application-level service accounts. Without documented procedures, there is no assurance that accounts are provisioned with appropriate least-privilege access, periodically reviewed, or deactivated upon personnel departure or role change.

**Evidence:**

- Examination of `deployment/terraform/iam.tf` reveals IAM bindings without documented approval workflow
- No account management SOP document found in `docs/` or `compliance/` directories
- ISSO interview (pre-assessment gap analysis) confirmed absence of formal provisioning/deprovisioning procedures
- GKE RBAC role bindings in `deployment/k8s/` lack documented review cadence

**Risk Level:** High — Unauthorized accounts or over-privileged accounts could enable unauthorized access to financial data (IT-004 PII) and governance policy configurations (IT-005). This violates SEC Reg S-P requirements for access controls protecting customer PII.

**Recommendation:**

1. Draft AC-2 account management procedures covering GCP IAM, GKE RBAC, and application service account lifecycle
2. Implement automated account review using GCP IAM Recommender
3. Establish periodic (quarterly) access review cadence enforced by ISSO
4. Document and enforce joiner/mover/leaver process

### FIND-002: IAM Bindings Overly Broad (AC-6)

**Control:** AC-6 — Least Privilege
**Severity:** High
**Status:** Open
**POAM Reference:** POAM-002
**Scheduled Completion:** 2026-05-15

**Description:**
Review of Terraform IAM configuration (`deployment/terraform/iam.tf`) reveals use of overly broad GCP IAM roles (such as `roles/editor` or broad project-level bindings) rather than purpose-specific custom roles implementing least privilege. This violates AC-6 Least Privilege requirements and creates an excessive attack surface if a service account or user credential is compromised.

**Evidence:**

- Terraform plan review of `deployment/terraform/iam.tf`
- Presence of broad project-level IAM bindings identified
- No evidence of custom IAM role definitions scoped to specific CAGE service functions

**Risk Level:** High — Overly permissive IAM bindings could allow a compromised service account to access, modify, or delete resources across the GCP project scope, including Cloud SQL financial data, GCS audit artifacts, and GKE cluster configuration.

**Recommendation:**

1. Enumerate all service accounts and their current IAM roles
2. Define and implement custom IAM roles scoped per CAGE service (gateway, OPA, NeMo, LangGraph)
3. Replace broad roles with purpose-specific bindings in `deployment/terraform/iam.tf`
4. Validate least-privilege posture with `terraform plan` and GCP IAM Recommender recommendations

### FIND-003: Audit Trace Generator Uses Synthetic Mock Traces (AU-12)

**Control:** AU-12 — Audit Record Generation
**Severity:** High
**Status:** Mitigated (2026-03-07) — `AgentBeatsSimulator` now gated by `CAGE_SIMULATION_MODE=true`
environment variable. Production KFP pipelines do not set this variable. Mock traces cannot
enter production audit pipeline without explicit opt-in. See `src/governed_financial_advisor/agents/evaluator/simulator.py`.
**POAM Reference:** POAM-003
**Scheduled Completion:** 2026-04-15

**Description:**
The audit automation script (`scripts/automated_auditor.py`) generates synthetic OpenTelemetry spans rather than connecting to the live Cloud Trace OTLP endpoint. This means that audit evidence produced by the automated auditor does not reflect actual system behavior, undermining the validity of ISO 42001 audit trail evidence and the integrity of the AU-12 control implementation.

**Evidence:**

- Code review of `scripts/automated_auditor.py` — synthetic trace generation confirmed
- No live OTLP endpoint connection found in auditor script
- Lula validation (`compliance/lula/lula-validation-au12.yaml`) may be validating against mock data
- ISO 42001 evidence stamps produced from mock traces may not reflect real inference behavior

**Risk Level:** High — Regulatory examinations (SEC Rule 17a-4, FINRA 4511) require that audit records reflect actual system activity. Synthetic audit trails constitute a material control failure that could result in regulatory penalties.

**Recommendation:**

1. Refactor `scripts/automated_auditor.py` to connect to live Cloud Trace OTLP endpoint
2. Validate that ISO 42001 evidence stamps are produced from real inference traces
3. Add integration test to `tests/` that verifies audit records are generated for actual inference events
4. Update Lula validation to test against live trace data

**Status:** Open
**POAM Reference:** POAM-006

**Status:** Open

**Risk Level:** Moderate — Financial data (IT-001) and PII (IT-004) transmitted without TLS would violate SEC Reg S-P, FINRA, and organizational policy.

**Recommendation:**

1. Add TLS 1.2+ assertion to `tests/test_gateway_connectivity.py`
2. Verify gRPC and REST endpoints enforce TLS with valid certificates
3. Add TLS test to CI pipeline as required gate

### FIND-009: Unpinned Python Dependency Version Specifiers (SI-2)

**Control:** SI-2 — Flaw Remediation
**Severity:** High
**Status:** Open
**POAM Reference:** POAM-013
**Scheduled Completion:** 2026-04-15

**Description:**
Python dependencies across CAGE services use `>=` version constraints rather than pinned versions in `pyproject.toml` and service `requirements.txt` files. This allows non-reproducible builds and uncontrolled dependency updates that may introduce vulnerabilities or break functionality.

**Evidence:**

- Examination of `pyproject.toml` — multiple `>=` version specifiers found
- Examination of `src/compliance_bridge/requirements.txt` and `src/governed_financial_advisor/requirements.txt` — non-pinned versions
- No `pip freeze` lockfiles found for any service
- Non-reproducible builds confirmed by dependency audit

**Risk Level:** High — Non-reproducible builds undermine supply chain integrity and make it impossible to guarantee that deployed artifacts match tested artifacts. A transitive dependency update could introduce vulnerabilities that bypass testing.

**Recommendation:**

1. Generate `pip freeze` lockfiles per service
2. Pin all dependencies to exact versions in requirements files
3. Integrate pip-audit into CI to detect version drift and known CVEs
4. Implement Dependabot or Renovate for automated dependency update PRs with testing

### FIND-010: CAGE_ROUTING_SEAL_SECRET Bypass (AC-3) — RESOLVED

**Control:** AC-3 — Access Enforcement
**Severity:** Critical
**Status:** Resolved
**POAM Reference:** POAM-012
**Resolution Date:** 2026-03-06

**Description:**
The `CAGE_ROUTING_SEAL_SECRET` environment variable, when unset or set to a development default value, previously bypassed cryptographic enforcement of governance routing seals. This allowed the critical safety control to be silently disabled in non-development environments without alerting operators.

**Evidence:**

- Code review of governance middleware confirmed bypass condition
- Remediation: `RuntimeError` now raised in non-development environments when `CAGE_ROUTING_SEAL_SECRET` is absent or matches known development defaults
- Monitoring alert added for bypass detection

**Residual Risk:** Low — Remediation verified by code review. Monitor alert for bypass conditions should be tested quarterly.

### FIND-011: No Intra-Cluster mTLS (IA-3)

**Control:** IA-3 — Device Identification and Authentication
**Severity:** Critical
**Status:** Open
**POAM Reference:** POAM-007
**Scheduled Completion:** 2026-07-31

**Description:**
Inter-service authentication within the GKE cluster relies solely on a shared `CAGE_ROUTING_SEAL_SECRET` HMAC rather than cryptographic mutual TLS (mTLS) providing per-service identity. Compromise of the shared secret undermines all service-to-service authentication claims simultaneously. Without mTLS, there is no cryptographic service identity verification.

**Evidence:**

- Architecture review of `deployment/k8s/` — no Istio service mesh or cert-manager configuration found
- No service mesh configuration in `deployment/terraform/`
- `deployment/k8s/network-policy.yaml` provides network-layer isolation but no mutual authentication
- Absence of mTLS confirmed by examination of inter-service communication patterns

**Risk Level:** Critical — Compromise of `CAGE_ROUTING_SEAL_SECRET` (a single shared secret) would allow an attacker to impersonate any CAGE service, bypass governance controls, and access financial data (IT-001) and PII (IT-004). This is the highest residual risk in the current architecture.

**Recommendation:**

1. Evaluate Istio service mesh or cert-manager for workload identity certificates
2. Implement mTLS for all intra-cluster service communication
3. Issue per-service certificates bound to GKE Workload Identity
4. Rotate `CAGE_ROUTING_SEAL_SECRET` immediately and implement automated rotation

### FIND-012: No Secret Rotation Schedule (IA-5)

**Control:** IA-5 — Authenticator Management
**Severity:** High
**Status:** Open
**POAM Reference:** POAM-014
**Scheduled Completion:** 2026-05-31 (mapped from POAM-014 SC-28)

**Description:**
No documented secret rotation schedule exists for CAGE credentials, including `CAGE_ROUTING_SEAL_SECRET`, database passwords, API keys for Langfuse and vLLM, and GCP service account keys. Long-lived credentials increase the window of opportunity for credential exploitation following disclosure.

**Evidence:**

- No secret rotation procedures found in `docs/` or `compliance/`
- Kubernetes secrets in `deployment/k8s/oscal-artifact-secrets.yaml` lack rotation metadata
- No GCP Secret Manager rotation configuration documented
- `deployment/scripts/update_langfuse_secret.py` exists but lacks automated scheduling

**Risk Level:** High — Long-lived credentials increase exposure window. A compromised credential with no rotation schedule could persist indefinitely, enabling continued unauthorized access.

**Recommendation:**

1. Define secret rotation policy: 90-day maximum lifetime for API keys, 180-day for certificates
2. Implement GCP Secret Manager with automated rotation for all CAGE credentials
3. Configure alerting for credential age exceeding policy thresholds
4. Document rotation procedures in `docs/SECRET_MANAGEMENT_OPTIONS.md`
