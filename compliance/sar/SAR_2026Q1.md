## 1. Executive Summary

### 1.1 Assessment Overview

This Security Assessment Report (SAR) documents the findings of the initial security control assessment of the Cybernetic AI Governance Engine (CAGE). This assessment was conducted as a pre-authorization gap analysis to characterize the current security posture of the system prior to the formal Security Assessment Plan (SAP) execution scheduled for 2026-Q2.

The assessment evaluated the CAGE system against the NIST SP 800-53 Rev. 5 **HIGH** impact baseline, focusing on 13 priority controls identified through gap analysis. The CAGE system is a novel AI/ML governance and inference gateway for financial services, deployed on Google Kubernetes Engine (GKE) and subject to financial regulatory requirements including SEC Rule 17a-4, FINRA Rule 4511, SEC Reg S-P, and Federal Reserve SR 11-7.

### 1.2 Overall Risk Posture

**Current Risk Rating: HIGH**

The CAGE system demonstrated significant security control gaps across access control, identification and authentication, audit and accountability, incident response, and supply chain risk management control families at the time of assessment. Key findings included:

- **3 Critical findings** — including absence of intra-cluster mTLS (FIND-011, subsequently closed 2026-05-17) and HMAC seal bypass vulnerability (FIND-010, resolved 2026-03-06)
- **10 High findings** — including absent account management procedures, overly permissive IAM bindings, no incident response plan, and no container vulnerability scanning
- **2 Moderate findings** — including no encryption-in-transit validation test and no SBOM generation

**RMF Completion Estimate at Assessment Date:** ~24% of the full authorization package complete. Critical gaps included:

- No System Security Plan (SSP)
- No Authorization to Operate (ATO)
- No formal Incident Response Plan (partially resolved by `docs/security/IR_PLAN.md`)
- No container vulnerability scanning in CI/CD
- No intra-cluster mTLS (closed 2026-05-17)

### 1.3 Positive Security Findings

The assessment identified the following areas of security strength:

- **9 NetworkPolicy objects** implementing default-deny posture across the GKE namespace
- **8-step governance pipeline** (NeMo Guardrails → OPA → STPA → CBF → Fiscal Limit → Consensus → Causal/FRIA)
- **AgentSight eBPF** monitoring providing kernel-level observability
- **OPA RBAC** with Rego policy enforcement for governance decisions
- **OpenTelemetry / Langfuse** audit trail infrastructure
- **ISO 42001 evidence stamping** on AI inference outputs
- **HMAC routing seal** enforcement (bypass remediated — FIND-010)
- **NeMo Guardrails Presidio** PII detection covering 15 entity types

### 1.4 Authorization Recommendation

Based on the findings at the time of assessment, the assessor **did not recommend ATO issuance**. Remediation of Critical and High findings — particularly mTLS (FIND-011, closed 2026-05-17), SSP (FIND-013), ATO package (FIND-014), and IRP (FIND-006) — is required before ATO can be recommended. A conditional ATO (IATO) may be considered by the AO if critical findings are remediated and remaining High findings are captured with credible remediation timelines in the POA&M.

## 2. System Overview

The Cybernetic AI Governance Engine (CAGE) is an AI-native financial advisory platform deployed on Google Kubernetes Engine (GKE) on Google Cloud Platform (GCP). The system orchestrates multi-agent LLM workflows for investment analysis and trade recommendations, enforcing governance policies via an 8-step governance pipeline.

**Key System Characteristics:**

- **Platform:** GKE, GCP-managed services (Cloud SQL PostgreSQL, GCS, Cloud Trace)
- **Application Stack:** FastAPI/gRPC gateway, NeMo Guardrails, OPA Policy Engine, LangGraph, Redis
- **AI/ML Components:** LangGraph Financial Advisor, vLLM inference, Vertex AI
- **Observability:** AgentSight eBPF, OpenTelemetry, Langfuse
- **Compliance Automation:** Lula (compliance-as-code), OSCAL, ISO 42001 evidence stamps
- **Security Baseline:** NIST SP 800-53 Rev. 5 HIGH

The system processes five information types including PII and individual financial records (C=High), which drives the overall HIGH system security category per FIPS 199. See `compliance/categorization/FIPS199_CATEGORIZATION.md` for full categorization detail.

## 3. Assessment Scope and Methods

### 3.1 Scope

This assessment covers the CAGE authorization boundary as defined in `compliance/boundary/AUTHORIZATION_BOUNDARY.md`. The 13 priority controls assessed are:

AC-2, AC-3, AU-2, AU-12, IA-3, IA-5, RA-5, SC-8, SI-2, CM-6, CM-8, IR-1, IR-6

GCP/GKE platform controls are inherited from Google's FedRAMP authorization and are not independently assessed herein.

### 3.2 Assessment Methods

Per NIST SP 800-53A Rev. 5:

- **Examination (E):** Review of IaC, Kubernetes manifests, source code, policies, Lula specs, and logs
- **Interview (I):** Discussions with system administrators, AI model operators, and compliance engineers
- **Test (T):** Lula validation execution, TLS endpoint tests, HMAC bypass scenarios, pip-audit, Trivy, red-team adversarial tests

### 3.3 Limitations

This is a pre-authorization gap assessment based on available documentation, code review, and automated tooling. The full formal assessment per the SAP (`docs/SECURITY_ASSESSMENT_PLAN.md`) is scheduled for 2026-Q2.

## 5. Detailed Findings

### FIND-001: No Account Management Procedures (AC-2)

**Control:** AC-2 — Account Management
**Severity:** High
**Status:** Open
**POAM Reference:** POAM-2026-001

**Description:**
No formal account management procedures existed at assessment time documenting the lifecycle management of user accounts, service accounts, and privileged accounts. This encompasses GCP IAM accounts, GKE Kubernetes RBAC role bindings, and application-level service accounts.

**Risk:** High — Unauthorized or over-privileged accounts could enable unauthorized access to financial data and governance policy configurations.

**Recommendation:**
1. Draft AC-2 account management procedures covering GCP IAM, GKE RBAC, and application service account lifecycle
2. Implement automated account review using GCP IAM Recommender
3. Establish periodic (quarterly) access review cadence
4. Document and enforce joiner/mover/leaver process

---

### FIND-002: IAM Bindings Overly Broad (AC-6)

**Control:** AC-6 — Least Privilege
**Severity:** High
**Status:** Open

**Description:**
Review of Terraform IAM configuration revealed use of overly broad GCP IAM roles rather than purpose-specific custom roles implementing least privilege.

**Risk:** High — Overly permissive IAM bindings could allow a compromised service account to access, modify, or delete resources across the GCP project scope.

**Recommendation:**
1. Enumerate all service accounts and their current IAM roles
2. Define and implement custom IAM roles scoped per CAGE service (gateway, OPA, NeMo, LangGraph)
3. Replace broad roles with purpose-specific bindings
4. Validate least-privilege posture with GCP IAM Recommender

---

### FIND-003: Audit Trace Generator Uses Synthetic Mock Traces (AU-12)

**Control:** AU-12 — Audit Record Generation
**Severity:** High
**Status:** Mitigated (2026-03-07)

**Description:**
The audit automation script generated synthetic OpenTelemetry spans rather than connecting to the live OTLP endpoint. This meant audit evidence did not reflect actual system behavior.

**Mitigation:** `AgentBeatsSimulator` is now gated by `CAGE_SIMULATION_MODE=true` environment variable. Production deployments do not set this variable. Mock traces cannot enter the production audit pipeline without explicit opt-in.

**Residual Risk:** Moderate — Mitigation verified by code review. Ongoing monitoring required.

---

### FIND-004: No Software Bill of Materials (SBOM) (CM-8)

**Control:** CM-8 — System Component Inventory
**Severity:** Moderate
**Status:** Open

**Description:**
No automated SBOM generation existed in the CI/CD pipeline. Container images and Python dependencies could not be rapidly audited against known CVE databases.

**Recommendation:**
1. Add Trivy SBOM generation (CycloneDX or SPDX format) to CI pipeline
2. Publish SBOM artifacts per container image build
3. Configure SBOM-based CVE alerting

---

### FIND-005: No TLS Enforcement Assertion in Gateway Test Suite (SC-8)

**Control:** SC-8 — Transmission Confidentiality and Integrity
**Severity:** Moderate
**Status:** Open
**POAM Reference:** POAM-2026-011

**Description:**
The gateway test suite did not assert that all connections use TLS 1.2 or higher. A misconfiguration could result in plaintext data transmission without triggering a test failure.

**Recommendation:**
1. Add TLS 1.2+ assertion to the gateway connectivity test suite
2. Verify gRPC and REST endpoints enforce TLS with valid certificates
3. Add TLS test as a required CI gate

---

### FIND-006: No Incident Response Plan (IR-1, IR-6)

**Control:** IR-1 — Incident Response Policy and Procedures; IR-6 — Incident Reporting
**Severity:** High
**Status:** Open (being remediated by `docs/security/IR_PLAN.md`)

**Description:**
No formal Incident Response Plan existed at the time of initial assessment. No documented procedures existed for detecting, reporting, containing, eradicating, or recovering from security incidents, including AI-specific incidents such as governance bypass events and prompt injection attacks.

**Recommendation:**
1. Draft and approve IRP per NIST SP 800-61 Rev. 2
2. Include AI-specific incident categories (governance bypass, model manipulation, PII exfiltration)
3. Define regulatory notification timelines
4. Conduct tabletop exercise within 90 days of IRP approval

### FIND-008: No Vulnerability Scanning in CI/CD Pipeline (RA-5)

**Control:** RA-5 — Vulnerability Monitoring and Scanning
**Severity:** High
**Status:** Open
**POAM Reference:** POAM-2026-010

**Description:**
The CI/CD pipeline did not include automated vulnerability scanning of Python dependencies or container images. Known CVEs in third-party libraries could be introduced and deployed without detection.

**Recommendation:**
1. Add Trivy container image scanning as a required CI step; fail builds on HIGH/CRITICAL CVEs
2. Add pip-audit Python dependency scanning as a required CI step
3. Establish patching SLA: Critical CVEs within 24 hours, High within 7 days

---

### FIND-009: Unpinned Python Dependency Version Specifiers (SI-2)

**Control:** SI-2 — Flaw Remediation
**Severity:** High
**Status:** Open
**POAM Reference:** POAM-2026-013

**Description:**
Python dependencies used `>=` version constraints rather than pinned versions, allowing non-reproducible builds and uncontrolled dependency updates.

**Recommendation:**
1. Generate lockfiles per service
2. Pin all dependencies to exact versions
3. Integrate pip-audit into CI to detect version drift and known CVEs
4. Implement Dependabot or Renovate for automated dependency update PRs

---

### FIND-010: CAGE_ROUTING_SEAL_SECRET Bypass (AC-3) — RESOLVED

**Control:** AC-3 — Access Enforcement
**Severity:** Critical
**Status:** Resolved
**Resolution Date:** 2026-03-06

**Description:**
The `CAGE_ROUTING_SEAL_SECRET` environment variable, when unset or set to a development default, previously bypassed cryptographic enforcement of governance routing seals.

**Remediation:** `RuntimeError` is now raised in non-development environments when `CAGE_ROUTING_SEAL_SECRET` is absent or matches known development defaults. Monitoring alert added for bypass detection.

**Residual Risk:** Low — Remediation verified by code review.

---

### FIND-011: No Intra-Cluster mTLS (IA-3) — CLOSED

**Control:** IA-3 — Device Identification and Authentication
**Severity:** Critical
**Status:** Closed
**Resolution Date:** 2026-05-17
**Remediation:** Linkerd mTLS implemented across all intra-cluster service communication in the `governance-stack` namespace. Per-pod cryptographic identity via SPIFFE/X.509 certificates issued by Linkerd CA.

**Description:**
Inter-service authentication within the GKE cluster relied solely on a shared HMAC secret rather than cryptographic mutual TLS providing per-service identity. Compromise of the shared secret would undermine all service-to-service authentication simultaneously.

---

### FIND-012: No Secret Rotation Schedule (IA-5)

**Control:** IA-5 — Authenticator Management
**Severity:** High
**Status:** Open
**POAM Reference:** POAM-2026-012

**Description:**
No documented secret rotation schedule existed for CAGE credentials, including the routing seal secret, database passwords, and API keys. Long-lived credentials increase the window of opportunity for credential exploitation.

**Recommendation:**
1. Define secret rotation policy: 90-day maximum lifetime for API keys, 180-day for certificates
2. Implement GCP Secret Manager with automated rotation for all CAGE credentials
3. Configure alerting for credential age exceeding policy thresholds
